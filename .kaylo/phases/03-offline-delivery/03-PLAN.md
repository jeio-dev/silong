## Design

Planner defaults unless Agreement identifies a user decision.

1. **Durable outbox.** Add local `static/outbox.js`, loaded before report.js, with a small vanilla JS API under a single namespace. IndexedDB database `silong-outbox`, version 1, stores `pending` keyed by client_id (immutable UUID/text/reporter/queued_at) and `receipts` keyed by client_id (id/confirmed_at, without report contents). Expose save, list-pending, list-receipts and acknowledge. Resolve writes only on transaction completion, rejecting on abort/error. Acknowledge inserts the receipt and deletes pending in one transaction, only after a successful hub response with a positive integer reference. Do not automatically expire, delete or edit unconfirmed reports. Audio is not implemented, but the record-based wrapper must not stringify payloads, leaving a path to Blob storage in phase 04. Partition naturally by browser origin; changing the hub URL changes the browser outbox origin and must be disclosed.
2. **Send loop.** On load, read pending and receipts; immediately attempt pending delivery. On submission, validate nonblank text, take a payload snapshot and UUID, await save, then update visible pending count and clear the submitted text so another report can be entered. Preserve the optional name. One sender per tab and one request at a time, FIFO by queued_at then client_id. Retry a snapshot of pending rows every five seconds while open; timers do not start overlapping passes. A failed request must not prevent trying other rows in the same pass. Keep the existing 20-second per-request timeout, so a hung request can delay later rows; disclose that five seconds is the idle retry interval, not a guarantee under a held request. Retry-now invokes the same guarded pass. Concurrent tabs may send the same row; server idempotency and idempotent acknowledgement keep one database report and one receipt. Do not add cross-tab leader election or another queue.
3. **Confirmation and errors.** Distinguish 'Saved on this phone; waiting to send' from 'Received by the hub: Reference #N'. Show a persistent pending count, each pending report's short text preview and current error, and confirmed references restored on reload. Keep server validation failures visible and retain those records; retry them on the normal schedule without modifying their payloads. Network/503/timeout/malformed success responses are unconfirmed and stay pending. If hub receipt succeeds but the acknowledgement transaction fails, show the known reference and storage warning, keep the in-memory receipt and durable pending row, and safely resend the same UUID later. A successful later acknowledgement clears the warning for that row. Never claim that hub confirmation failed just because local bookkeeping failed.
4. **Storage failure path.** Any open/read/save failure produces an explicit Taglish-friendly warning, with no claim of durable storage. A new report whose save fails gets exactly one immediate request, with its original UUID; if it fails, leave the form payload intact/frozen and show 'Not saved on this phone; not confirmed; no automatic retry'. Offer manual retry with the same UUID and allow a new report without claiming the old one was sent; retain the failed in-memory item visibly while the page remains open. Never put that item into the automatic loop until a later explicit save succeeds. If reading an existing outbox fails, never overwrite/clear it or imply zero pending; show 'Pending count unavailable'. Existing saved records resume when storage reads work. Blocked upgrades, transaction aborts and quota errors must settle as visible failures rather than hanging the UI; use a bounded open timeout and close on versionchange.
5. **Phone page.** Replace phase 01's no-offline-save note and abandon-pending flow. Form feedback and queue/reference lists use labelled DOM nodes and role=status without announcing the entire list every five seconds. Keep tap targets >=44 px, keyboard focus and draft text across background retry updates, and distinguish unsaved drafts from submitted pending snapshots. Warn to keep the tab open, that a first load/offline reload cannot fetch an unreachable hub, and that the saved outbox resumes when this same address loads again. No cancellation or pending-report editing feature in this phase.
6. **Phone URL and QR — user's selected setup.** Add optional `SILONG_HUB_URL`, normalized to a plain HTTP origin with numeric non-loopback IPv4 address and optional port (default HTTP port 80), with a trailing slash; reject credentials, query, fragment, non-root paths, wildcard/loopback addresses and HTTPS. Keep Config's new field optional with a default so existing positional/keyword test construction remains valid. When unset, use the request origin only when it has an eligible numeric IPv4 host; otherwise return no phone URL, explain to open the board via the Wi-Fi IPv4 address or set the override, and suppress the QR. Never advertise localhost or 0.0.0.0 as phone addresses. Do not discover adapters or alter firewall/WSL networking. An override must point to the prepared hub; syntax validation is not proof of LAN reachability. The user opens the board by LAN address or supplies the override once. Use the same resolver for status and GET `/api/qr`; SVG encodes exactly that URL and is generated locally by qrcode. QR returns 409 with a useful detail if no valid phone URL is available. Cache-Control: no-store on both endpoints; no request/Host-dependent shared QR cache. The final phone scan remains phase 05.
7. **Status contract.** GET `/api/status` returns `hub_url` (string|null), `model` (configured tag|null), `model_state` (`not_configured`, `loaded`, `not_loaded`, `unavailable`), `model_checked_at` (UTC ISO timestamp|null), `worker_running` (bool), `audio_available:false`, `queue_length` (status queued), `processing_count` (transcribing/extracting), `reports_today`, `local_date` (hub calendar date), `urgency_counts` (critical/high/medium/low, unresolved and classified only), and `snapshot_at` (UTC ISO). Obtain all counts from one db.list_reports snapshot, parsing created_at as aware UTC then converting to the hub's local date. Reports today includes resolved and failed rows. Failed/edited completed reports are not waiting queue entries. Storage failure remains 503 with the existing message.
8. **Model availability.** A status request with no configured model does not import/probe Ollama. Otherwise make an asynchronous GET to the local `/api/ps` using the existing resolver, with a total wall-clock bound of one second; no generate/chat/load call and no added thread. An exact loaded tag match (name/model, with missing tag normalized to :latest) produces loaded; a valid response without that model produces not_loaded; timeout, bad JSON/schema or HTTP failure produces unavailable. Display 'Loaded in Ollama (last checked ...)' or 'Not loaded', never claim inference correctness or accepted speed. Show worker not running distinctly even if a model is loaded. Keep the model check isolated to this endpoint; report receipt and list polling never await it. No new cache/monitor daemon; two-second status polling is adequate for this local demo.
9. **Board header.** Poll reports and status independently every two seconds with separate in-flight guards/timeouts. A status timeout must not prevent cards from updating. Keep last successful values with a specific stale-status warning; never substitute zero for unavailable counts. Show the matching clickable phone URL and QR, model and check time, 'Text only: audio unavailable', queued/processing counts, reports today and four urgency counts. Refresh QR only when URL changes, and hide old QR immediately when URL becomes unavailable. Header uses readable words and strong contrast; widen/resize shared styles as needed without sacrificing the phone form or inline editor. Existing cards/actions/original expansion/draft preservation remain acceptance criteria. Same-host 412x915 and 1280x900 views establish layout; across-room/projector usability is not verified here.
10. **Delivery order.** Implement T1, T2, T3, T4, T5 sequentially with per-task checks and commits under GITFLOW. If time prevents completion, record the incomplete task; do not silently cut demo-gating offline delivery or QR. Phase 04 stays optional audio and phase 05 stays disconnected verification; no later-phase folder is created now.
