# 02 Local AI triage and staff corrections: queued reports become locally extracted, rule-prioritized, correctable cards

Status: Current

## Goal and scope

A persistent in-process worker takes the oldest queued text report, extracts the PRD's fixed fields with a local Ollama model, and code assigns urgency and a plain-language reason. The board shows classified reports sorted by urgency, with extracted details, originals and measured extraction time; unclassified work (queued, extracting, failed, never extracted) stays conspicuous and is never shown as Low. Staff can correct every extracted field (urgency is recomputed), complete a failed or unprocessed report by hand, retry a failed report, and resolve or reopen a report. Restarting the hub resets interrupted extraction to `queued` and resumes it, keeping originals, staff edits and resolved state. A five-report synthetic Taglish test on the Ryzen 5 2400G hub records expected versus actual extraction, priority and measured times so the user can choose the model and speed target.

PRD criteria advanced: 3 (slow or unavailable model never delays receipt), 5 (urgency fixtures, precedence, reasons, sorting, edits), 6 (failure, retry, manual completion, restart recovery), 8 (five-report test), and the classified/resolved parts of 7. Criterion 1 is advanced on this host only; its A54 disconnected check is phase 05.

Excluded (later phases): IndexedDB outbox and automatic phone retries, hub URL/QR, model-readiness and count header, reports-today and per-urgency counts (03); audio, Whisper, `transcribing` and `asr_ms` (04); Windows/A54 demo verification, README benchmarks section beyond this phase's measured results, demo video (05). No stretch capabilities. Issue #4 (open LAN board/API, no intake limits) stays deferred by the user until all phases are done.

Constraints: Python stack and dependencies from phase 01 (no new runtime dependency is needed: `httpx` is already pinned); one process plus one worker thread; the `reports` table is the queue. Ollama requests use `keep_alive: -1`, `options.temperature: 0`, `think: false`, `stream: false`, and `format` set to the extraction JSON schema, with a fixed prompt prefix and the report text last. Urgency is computed by code. Render report content with `textContent`/DOM creation only. Synthetic reports only in tests, fixtures and evidence. Do not modify or stage `IDEA.md`, `PRD.md`, `GITFLOW.md`, `CLAUDE.md` or `AGENTS.md` unless the user assigns it. Every displayed timing is measured; no platform or performance claim beyond recorded evidence.

## Design

Planner defaults unless marked as a user decision in Agreement.

1. **Modules.** Add `silong/rules.py` (field validation, urgency, sort key; pure functions), `silong/extract.py` (schema, fixed prompt, Ollama client), `silong/worker.py` (thread), `silong/bench.py` (five-report test runner, `python -m silong.bench`). Extend `db.py` and `app.py`. No new dependency.
2. **Fields.** Stored in `fields_json` with exactly the keys `location` (string|null), `in_center` (bool|null), `on_behalf` (bool|null), `headcount` (integer ≥ 0|null), `vulnerable` (unique list from `senior, pwd, infant, child, pregnant, sick`), `injured` (bool), `injury_note` (string|null), `needs` (unique list from `rescue, medical, medicine, food, water, milk_formula, hygiene, other`), `summary` (string; a blank, whitespace-only or null summary is stored as `""`, never null, so manual completion does not require a summary). `rules.validate_fields` is the single validator for model output and staff edits: it rejects missing/extra keys and wrong types or enum values (`ValueError` with a useful message), strips strings and turns blank strings into null (except `summary`, which stays `""`), and de-duplicates lists in canonical order. Model summaries longer than 20 words are cut to the first 20 words; a staff summary over 20 words is rejected with 422.
3. **Urgency** (`rules.classify(fields) -> (urgency, reason)`, first match wins): `critical` "Critical: rescue needed outside center" (rescue and `in_center is False`); `critical` "Critical: rescue needed" / "Critical: medical need" / "Critical: injury reported" (first of rescue, medical, injured present); `high` "High: <vulnerable joined by ', '> + <matching needs among medicine, milk_formula, water, food, joined by ', '>", e.g. "High: infant + milk_formula"; `medium` "Medium: needs <needs joined by ', '>"; `low` "Low: no need stated". `in_center` null never triggers the outside-center rule but still allows the general rescue rule.
4. **Ordering.** `GET /api/reports` returns rows already ordered: unresolved classified first by urgency rank (critical, high, medium, low), then oldest `created_at`, then larger headcount (null last), then `id`; then unresolved unclassified, oldest first; then resolved, newest receipt first. "Classified" means `urgency` is not null. The board groups by section in that order but displays unclassified **above** the classified list so new and failed work stays conspicuous; it never re-sorts.
5. **Extraction.** `POST {ollama}/api/chat` with `model`, `messages` = fixed system prompt (rules: extract only what is stated; unknown location/headcount/flags stay null, lists empty, never guess headcount; `location` is where the people in need are; `in_center`/`on_behalf` meanings; `injured` false when no injury is stated; English summary ≤ 20 words) + 2–3 synthetic Taglish few-shot user/assistant pairs (covering an outside-center rescue reported on behalf of others, an in-center vulnerable person with a supply need, and a report with unknown headcount/location) + the report as the final user message, `format` = the JSON schema, `stream: false`, `think: false`, `keep_alive: -1`, `options: {"temperature": 0}`. The prefix is a module constant so it is byte-identical for every report. Ollama's address is `OLLAMA_HOST` (Ollama's own variable; bare `host:port` gets `http://`; a `0.0.0.0` or `::` host, which is a listen address such as the user's Windows setting, maps to `127.0.0.1`), default `http://127.0.0.1:11434`. This reads a configuration input beyond the four `SILONG_*` variables; it is a planner default that the user confirms with the phase summary. Timeouts: 10 s connect, 300 s read (CPU cold load can be slow). Any connection error, HTTP error, non-JSON content or `validate_fields` failure raises `ExtractionError` with a short staff-readable message (for example "Ollama is not reachable at http://127.0.0.1:11434" or "Model reply did not match the report fields: headcount must be an integer").
6. **Worker.** Started by the lifespan only when `config.model` is set; with no model, no thread starts, reports stay queued and staff can complete them by hand. One daemon thread: on start it sends one warm-up request (load the model with `keep_alive: -1`, failure only logged), then loops: claim the oldest `queued` row in a `BEGIN IMMEDIATE` transaction (set `status='extracting'`, clear `error`), extract, then either save (`fields_json`, `urgency`, `urgency_reason`, `llm_ms`, `status='done'`, `error=NULL`) **only if the row is still `extracting` and `edited=0`**, or mark `failed` with the message (only if still `extracting`). `llm_ms` is wall-clock milliseconds around the Ollama call (`time.monotonic`). Idle waiting uses a `threading.Event` set by receipt and retry, with a 2 s timeout fallback. Every loop iteration is guarded: any non-`ExtractionError` exception from the extractor marks the claimed row `failed` with "Unexpected processing error; retry or complete by hand" and logs the traceback; a `sqlite3.Error` in claim is logged and the claim is retried after the idle wait; a `sqlite3.Error` in save or mark-failed is logged and that same guarded write is retried with the held result after the idle wait until it succeeds or the worker is stopped (it never moves on and leaves the row `extracting`). The thread exits only when stopped. Shutdown sets the stop flag and the wake event and joins the thread for up to 5 s; it is a daemon so a stuck Ollama request cannot block process exit. Tests release fake extractors before closing the client. `create_app(config, *, extract=None, warm_up=None)` passes `extract` (default `silong.extract.extract` bound to the model) and `warm_up` (default `silong.extract.warm_up`; a no-op whenever `extract` is injected) to the worker so tests inject fakes and never reach Ollama; a warm-up failure of any kind is only logged; `silong.worker` and `silong.extract` are imported inside the lifespan only when a model is set. `ApiTestCase` builds apps with `model=None` unless a test opts in with a fake extractor, and `_running_hub` removes `SILONG_MODEL` and `OLLAMA_HOST` from the copied environment before adding its own values. Resolved-but-queued reports are still processed. An unreachable Ollama marks each claimed report `failed` with the reachability message; staff retry.
7. **Restart recovery.** Lifespan, after `init_db` and before the worker starts: `UPDATE reports SET status='queued' WHERE status IN ('transcribing','extracting')`. Originals, `fields_json`, `edited`, `resolved` and timings are untouched; edited rows are never in those states (see 8).
8. **Staff API.** `PATCH /api/reports/{id}` parses `await request.json()` itself (no Pydantic body model) so every 422 `detail` is a single human-readable string; JSON body with `fields` (full field object) and/or `resolved` (bool); anything else, an empty body, or invalid fields → 422; unknown id → 404. Saving `fields` validates, recomputes urgency/reason, sets `edited=1`, `status='done'`, `error=NULL` in one transaction, regardless of the previous status (this is manual completion for queued/extracting/failed rows; a later worker result for that row is discarded by the guard in 6). `resolved` sets or clears the flag on any report. `POST /api/reports/{id}/retry`: only `status='failed'` → `queued`, `error=NULL`, wakes the worker, 200 with the view; other states → 409; unknown → 404. Responses return the same report view as the list. Storage errors → 503 as in phase 01.
9. **Board.** Sections: "Not yet triaged" (unresolved, no urgency; status text per state: Queued / Extracting / Failed with the error and a Retry button), "Triaged" (sorted; urgency label in words plus color band, reason, location, "In center: yes/no/unknown", "Reporting for others: yes/no/unknown", headcount or "unknown", vulnerable tags, needs, summary, "Edited by staff" marker, "Extraction took N.N s" only when `llm_ms` is present), and "Resolved" (collapsed list, Reopen button). Every card shows reference, receipt time, reporter, and the original text (in an expandable block on triaged cards). Each unresolved card has Edit and Resolve. Edit opens an inline form for all nine fields (text inputs, number input, yes/no/unknown selects, checkbox groups), prefilled from the current fields or, for a report with none, blank text, "unknown" selects, empty checkbox groups and injured unchecked. If a poll shows the report changed (status, fields or urgency) while the form is open, the form stays but shows "This report changed since you opened the editor" so staff can cancel and reopen it. Save sends the full object and shows the server's 422 message on failure. Polling keeps running but must not replace a card whose edit form is open or lose expanded-original state; other cards still update. Buttons ≥ 44 px, labelled controls, visible focus, `role="status"` feedback; data via `textContent`/DOM creation only.
10. **Five-report test.** `tests/fixtures/five_reports.json`: five synthetic Taglish reports with expected fields and priority covering Critical outside-center rescue on behalf of others, Critical injury in center, High vulnerable + supply need, Medium other need, Low no need. `python -m silong.bench --model TAG [--out PATH]` first unloads every model listed by `/api/ps` (request with `keep_alive: 0`), records `/api/ps` and total/free memory (Windows figures via `wsl` interop where available, otherwise marked not recorded), warms the model once (load time recorded separately as cold load), then runs the five reports through `extract.extract` one at a time, printing and writing Markdown with: environment (CPU, OS/WSL, Ollama version from `/api/version`, model tag and size from `/api/tags`), each source text, expected and actual fields, per-field matches, expected and actual priority, and measured `llm_ms`. Evidence goes to `.kaylo/phases/02-local-triage/02-MODELS.md`. The same fixture file feeds a rules unit test (expected fields → expected priority) so fixtures and rules cannot drift.
11. **Cut order if time runs short** (about 10 hours remain before the freeze, with phases 03–05 to follow). PRD criteria 3, 5 and 7 gate the demo; 6 and 8 are measure-and-disclose. Protect T1, T2, T4, T5, T6 and T8's edit-and-recompute path.
