# 01 Durable intake: phone reports reach a persistent local staff board

Status: Current

## Goal and scope

Deliver the first runnable slice: a phone can submit a synthetic Taglish text report over local HTTP, receive a hub reference number after durable storage, and find the original report on the polling staff board. Repeated delivery of one client UUID creates exactly one report, including across application restarts. Submission requires no model or internet connection.

This is an intermediate slice of `PRD.md`, not demo readiness. Included here: Python runtime/configuration, SQLite intake, text submission/list APIs, local static reporter/board pages, and setup/check instructions. Later phases deliver inference and prioritization, staff editing/resolution/retry, IndexedDB offline delivery, QR/status details, optional audio, and target-hardware/demo evidence. No stretch capabilities enter scope.

Constraints: Python 3.11+, FastAPI/uvicorn, SQLite from the standard library, plain HTML/vanilla JavaScript and one shared CSS file; one application process. Do not modify or stage the user's documents (`IDEA.md`, `PRD.md`, `GITFLOW.md`, `CLAUDE.md`, `AGENTS.md`) unless the user assigns the change to a task. Report contents never leave the local hub/browser. Do not introduce auth, frontend compilation, CDN assets, cloud inference, service workers, or platform verification claims beyond actual evidence.

## Design

Planner defaults, pending confirmation of the phase summary:

1. Use a small `silong/` package: `config.py`, `db.py`, `app.py`, `__main__.py`, and `static/` containing `index.html`, `board.html`, `report.js`, `board.js`, and `style.css`. Use a FastAPI app factory for isolated tests, its lifespan for database initialization, and `python -m silong` as the launcher. Avoid a general framework or service/repository abstraction beyond the small database helper.
2. Base dependencies in `requirements.txt`: FastAPI, uvicorn, httpx (also required by the later Ollama integration and FastAPI TestClient), and python-multipart. Pin versions actually installed and checked during T1; do not guess current compatibility. Optional Whisper and QR dependencies are added only when their phase needs them. Use standard-library `unittest` for checks, including TestClient for API behavior, and temporary directories/databases. No Node dependency or testing framework is needed.
3. Configuration supports `SILONG_MODEL` (optional until inference is introduced), `SILONG_WHISPER` (`small`, `base`, `off`; off when absent), `SILONG_PORT` (8000 when absent), and `SILONG_DB` (`silong.db` when absent). Validate invalid values with useful startup errors. This phase does not load Whisper or Ollama even when a selection is configured. Launch uvicorn on `0.0.0.0` with one process, no reload, and the configured port. Document a manual LAN-IP discovery step in the initial README; automatic URL detection/override and matching QR belong to phase 03.
4. Use the `reports` table outlined in `IDEA.md`, retaining the future queue, transcription, extraction, timing, error, edited, and resolved columns. `client_id` is UNIQUE and NOT NULL, `id` is an integer reference that is never reused (SQLite AUTOINCREMENT), `created_at` is assigned by the hub in UTC, and new rows have `status='queued'`, null classification/timings, `edited=0`, and `resolved=0`. Receipt does not fabricate extracted fields or priority. Store the original entered text and optional reporter name; use trimmed text only to validate that content is nonempty.
5. Use a connection per operation, parameterized SQL, finite busy timeout, and explicit short transactions. Concurrent requests with one UUID use conflict-safe insertion/readback to return the original row. Commit before acknowledgement. A duplicate payload never overwrites originals. Database errors return failure rather than a confirmed reference. Worker claiming/recovery, edits, and model-result races are designed in phase 02 when the worker is introduced.
6. API contracts: `POST /api/reports` accepts multipart `client_id` (canonical UUID string), `text` (non-whitespace), optional `reporter`; returns HTTP 200 `{ "id": <integer>, "status": <stored status> }` for new and repeated receipt. A repeated valid client UUID returns the original stored report even if its submitted text differs. This phase rejects an audio attachment explicitly with 422 rather than silently ignoring it, and shows no audio control. Invalid/missing UUID, empty text, or name-only submission returns 422 without inserting a row. Storage failures return 503 with a useful generic message; never display a receipt for a failed request. `GET /api/reports` returns a JSON array of stored rows, including null `fields`, null urgency/reason/timings, original text, reporter, status, error and resolved flags, ordered oldest receipt first with `id` as a deterministic tie breaker. `GET /` and `/board` serve local static pages; `/static/` serves assets. Classification sorting is added in phase 02; future PATCH/retry/status/QR routes are not mocked as working.
7. The intermediate form makes one immediate send and displays a confirmed number only after a successful hub response. Generate a UUID v4 with `crypto.getRandomValues`, which works on local HTTP; do not depend on secure-context-only `crypto.randomUUID`. Retain the UUID and submitted payload in memory while an acknowledgement is uncertain so an explicit retry sends the same submission. Freeze that payload until acknowledgement or an explicit new-report action. Explain that automatic offline saving/retry arrives in phase 03; do not promise it here. Final PRD IndexedDB behavior is unchanged by this temporary slice.
8. The board polls every two seconds, displays original text/name/reference/receipt/status in an unmistakable unclassified section, and shows a connection/stale-data indication after a poll failure without erasing the last successful view. Never label queued work Low or show invented processing times. Use `textContent`/DOM creation for report data, local assets only, responsive layout, keyboard-visible focus, labelled controls, accessible feedback, and at least 44px tap targets. Priority colors are introduced with text labels in later work.

Technical references checked during planning: FastAPI documents the required [python-multipart dependency for forms/files](https://fastapi.tiangolo.com/tutorial/request-forms-and-files/) and recommends [lifespan for startup/shutdown](https://fastapi.tiangolo.com/advanced/events/). MDN confirms [getRandomValues works in insecure contexts](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/getRandomValues), as needed for local HTTP. No benchmark, model-availability, or Windows compatibility claim follows from these references.
